内容提取日期：2026年10月18日。资料版本：`chengxing-demo-v1`。

本文件供人工查阅项目业务知识、核对设计依据和了解实际处理流程。第一部分汇总当前完整产品目录；第二部分保留正式知识库6篇正文、24个小节的全部文字，仅调整标题层级；第三部分将主要业务规则对应到实际代码。读者可以先读总览，再按问题查阅原文和出处。

澄星协作是本项目采用的合成团队协作SaaS产品。澄星售前助手负责解释资料、处理需求、选型计价和内部草案流程；资料中的API、Webhook、SSO等是被咨询产品的能力。本文按当前资料与实现整理，供理解这套合成业务及其处理设计。

### 完整适用条件

**兼容身份提供方前提**（`saml_sso_compatible_idp`，关联`saml_sso`）：使用澄星协作的 SAML SSO 时，客户须明确确认已具备兼容的身份提供方。

本版只有上述一个受控适用条件。资料解释规则，用户明确自述说明客户目前的情况，实际检索证据还需在本次业务链中有效；三者各有用途。

### 选型判断中的几个区别

- 支持：目录有明确能力记录；带条件的能力仍需核对前提。
- 不支持：目录明确记为不支持，例如三档的私有化部署。
- 未知：具体要求未建模或资料未说明，例如某种导出格式、限流参数、SCIM自动开通。
- 待确认：客户情况或必要参数尚未明确，不能猜测补齐。

### 从知识到一次使用过程

选型与草案：客户说明功能要求 → 模型提出候选并独立核对 → 程序接受需求 → 按目录匹配 → 补明确购买参数 → 程序计算基价 → 展示待确认草案 → 用户点击 → 保存并按编号查回。

资料咨询：用户提出具体问题 → 检索本地知识小节 → 取得实际原文与来源 → 选择并检查引用及问题归属 → 展示引用和采用依据。

例如，已明确要求API与Webhook、实际购买18席、订阅9个月时，目录中的最低满足档为Team，订阅基价为80×18×9＝12,960元。明确改为6个月后应为8,640元。这里是规则算例，不是新增的当次模型测试结果。

#### 产品身份与资料用途
澄星协作是面向团队任务与项目协作的合成 SaaS，产品内部编号为 chengxing_collab。本文适用于了解产品用途、准备提出协作需求的使用者。澄星售前助手用于核对需求、解释套餐差异和适用条件，是介绍产品的助手，并非另一款产品。本资料集供单用户本地演示使用，其中的能力是既定演示产品事实，不表示当前助手已经实现协作系统。阅读资料时应区分产品说明、客户需求和助手实际执行的功能，不能把产品能力名称当作本项目已经提供的外部服务。

#### 从协作目的形成明确需求
适用对象是希望围绕任务和项目开展基础协作的团队。可以先说明要解决的工作问题，再区分必须具备的能力与希望了解的细节；任务与项目协作、基础成员角色和数据导出在三档套餐中均有记录。仅有“让工作更方便”或“功能越多越好”这样的表达，还不足以形成明确的硬需求。任务工作流、甘特图和自动化未在本版目录中建模，不能因为基础协作受支持就承诺这些细节。公司人数也不决定套餐档位，应依据实际功能需求理解各档差异。

#### 三档套餐的能力层次
基础版 Basic、团队版 Team、企业版 Business 是同一产品的三档有序套餐，适用于比较基础协作、系统集成和企业管理需求。Basic 包含任务与项目协作、基础成员角色和数据导出；Team 在这些能力上增加产品 API 与 Webhook 通知；Business 继续包含这些能力，并增加 SAML SSO 与审计日志。这个层次说明目录中的包含关系，不等同于对任何客户都能直接使用的保证。SSO 有独立适用条件，私有化部署在三档中都不支持，最高档名称不能覆盖这些限制。

#### 支持记录与客户适用性
适用对象是需要比较套餐是否满足自己要求的读者。产品目录的“支持”回答某档是否具备指定能力；客户适用性还需要保留明确要求、未说明的细节和相关条件。不能仅凭套餐名称、公司规模或最高档就得出完全满足的结论。没有明确硬需求时可以了解目录，不能宣称选型已经完成；资料没有回答某项要求，也不能自动改写成不支持。用户主动选择较高且满足需求的档位可以记录其选择原因，但不会改变目录事实或删去原有的硬需求。

### 2 基础协作能力的含义与限制

#### 任务与项目协作
任务与项目协作适用于希望围绕任务和项目开展基础团队协作的客户，Basic、Team、Business 三档均支持。能力名称表达协作用途，不逐项说明界面、流程或自动处理方式。客户若提出工作流、甘特图、自动化等具体子功能，应将原始要求单独保留，因为本版目录并未建模这些内容。不能将相近的使用场景直接合并为已支持的功能，也不能把使用者对某种工作方式的偏好转成产品承诺。说明基础协作时应同时保留这些细节限制，避免只引用支持结论。

#### 基础成员角色
基础成员角色适用于需要区分成员基础角色的团队，Basic、Team、Business 三档均支持。本版资料只说明存在基础角色区分，没有定义角色名称、角色数量和具体权限清单。自定义角色、细粒度权限和身份同步不能直接归入这项能力；如果这些内容是客户的硬需求，应作为尚未建模的要求继续保留。角色说明也不证明某个成员可以执行指定管理操作。讨论权限细节时需要具体资料依据，不能从“基础成员角色”这一名称推导任意授权规则或额外身份功能。

#### 协作数据导出
数据导出适用于需要将协作数据导出的客户，Basic、Team、Business 三档均支持。本版说明的是能力存在，未规定导出格式、容量、频率和覆盖范围。用户提出指定文件格式、完整历史导出或定时导出时，应区分这些细节与一般的数据导出需求，不能自动认定都已满足。也不能因细节未说明就把三档的数据导出能力改写为不支持。导出用于取得数据的含义与产品 API 集成、Webhook 通知不同，支持一种能力不能作为另两种能力的证明。

#### 能力名称的解释边界
本节适用于已经有具体功能清单、希望对应产品能力的客户。八项受控能力有各自稳定身份，正文解释帮助理解其含义，但不会新增支持矩阵中的能力。基础角色与身份同步、数据导出与双向同步、SAML SSO 与 SCIM 自动开通都不能因名称接近而相互替代。对于目录外要求，资料应保留“未说明”的事实和客户原意，而不是自行选择最相似的能力后宣告支持。未知要求得到新资料前仍需明确处理，增加解释文字不等于已经扩大产品能力或完成需求判断。

### 3 产品 API 与 Webhook 的集成说明

来源：`app/data/knowledge/03_api_webhook.md`；文档编号：`api_webhook`；共4个完整小节。

#### 产品 API 的适用范围
产品 API 适用于明确需要 API 集成能力的客户，Team、Business 支持，Basic 不支持。本版目录确认能力是否提供，未说明具体接口、鉴权方式、限流和同步行为。客户提出某个接口、某种认证机制或某个调用量要求时，不能仅凭 API 受支持就认定这些细节成立。API 能力也不证明已经与客户的系统完成集成；本文是售前产品说明，不是可执行接口文档。需要技术参数的需求应保留原话和待确认细节，避免把实现方式补成新的购买条件或服务保证。

#### Webhook 通知的适用范围
Webhook 通知适用于明确需要产品以 Webhook 发出相关事件通知的客户，Team、Business 支持，Basic 不支持。本版未列出事件清单、通知负载、投递时效和失败处理参数，因此不能承诺任意事件都可通知，也不能推断某种重试或送达保证。Webhook 通知表达事件发出的能力，不自动等于客户系统与产品之间持续保持双向一致。若客户关心指定事件或处理可靠性，需继续保留这些具体要求，不能因套餐包含 Webhook 就把未说明的部分一并判定为支持。

#### API 与通知承担不同用途
本节适用于同时考虑 API 与 Webhook 的 Team、Business 客户。API 集成和事件通知是两个分别记录的能力，介绍方案时应指出客户实际需要其中哪项或两项；Basic 对两项均不支持。收到事件通知与调用产品接口不是同一行为，不能用一项替代另一项，也不能从两项同时存在推导完整双向同步方案。本版资料没有提供集成步骤、第三方兼容清单或性能承诺。对客户已有系统如何配合，应先确认目标行为与尚待说明的细节，不将泛泛集成意愿补成已经实现的连接。

#### 含糊的系统对接要求
本节适用于只提出“对接现有系统”而未说明方式的客户。“对接”可能涉及 API、事件通知、数据导出或其他尚未建模的行为，不能直接替客户决定为明确 API 需求。可先了解期望的数据流向和需要的动作，再保留哪些能力已明确、哪些技术细节尚未说明。Team、Business 对 API 和 Webhook 的支持只能说明对应能力存在，Basic 的数据导出也不能代替任何集成要求。若要求涉及未建模技术参数或目录外能力，应继续表达未知，不能通过改写需求得到表面的满足结论。

### 4 SAML SSO 的前提与配置概念

来源：`app/data/knowledge/04_saml_sso.md`；文档编号：`saml_sso`；共4个完整小节。

#### 企业版 SSO 的唯一适用前提
本节适用于企业版 Business 的 SAML SSO 需求；Basic、Team 不支持该能力。使用澄星协作的 SAML SSO 时，客户须明确确认已具备兼容的身份提供方。这是唯一受控适用前提，关联条件 saml_sso_compatible_idp 与能力 saml_sso。用户明确不具备时，当前 SSO 需求不满足；情况未知或答复有歧义时，前提待确认；未来计划准备不能当作当前具备。对用户明确具备的情况，仍须有有效条件资料，判断基于其明确自述，助手不连接客户身份系统验证真实环境。

#### 统一登录的概念范围
本节适用于希望理解 Business 中 SAML SSO 用途的客户，Basic、Team 不支持该能力。SAML SSO 表示采用 SAML 的单点登录能力，可以用来理解统一登录的产品方向；本版没有扩展为所有身份协议都可使用。员工已有公司账号的描述也没有说明具体身份协议或系统兼容情况，不能单凭这个描述得出适用判断。完整适用规则应阅读本篇的唯一前提小节。SCIM 自动开通是另一个要求，不属于此能力的已证明范围，不能用 SSO 支持记录回答账户自动创建或同步问题。

#### 管理员配置与购买前提
本节适用于了解 Business 的 SAML SSO 实施概念的客户。管理员后续配置属于实施说明，不增加第二个购买前提。当前资料没有规定配置字段、交换步骤、证书管理、具体身份提供方品牌或兼容版本，不能自行补出操作手册，也不能承诺任意身份系统均可直接连接。若客户需要配置细节，应保留其具体问题，继续核对资料范围；有关客户是否适用的判断仍依据本篇唯一前提小节。这里解释配置与售前判断的区别，不表示助手已经执行登录配置或验证客户环境。

#### 条件资料与用户事实的区别
本节适用于核对 Business 的 SAML SSO 需求时区分两类依据的读者。产品条件资料用于解释规则，用户明确自述用于记录客户情况，两者不能相互冒充。完整规则见本篇唯一前提小节；Basic、Team 的能力不支持记录不会因用户情况改变。有资料正文并不等于某次检索已取得有效证据；资料版本、条件关联或来源无效时，应保留阻断原因，已知相关冲突也不能直接通过。仅有产品条件的一句说明，或仅有用户肯定答复，都不足以证明后续真实证据链已经成立。

### 5 审计日志与数据导出的区别

来源：`app/data/knowledge/05_audit_export.md`；文档编号：`audit_export`；共4个完整小节。

#### 审计日志的套餐范围
审计日志适用于明确需要产品审计记录能力的客户，Business 支持，Basic、Team 不支持。支持记录不要求客户同时提出 SSO 需求，也不能因企业版同时有 SSO 就把它的前提套到无关的审计要求上。当前资料未规定哪些动作进入日志、记录字段或可查询方式。客户要求某类活动必须可追踪时，应将该细节保留下来，不能只用“审计日志受支持”回答完整需求。产品能力事实与每一项具体审计场景的满足情况应分别说明，避免把能力名称当作覆盖清单。

#### 审计能力与合规承诺
本节适用于需要 Business 审计日志并关心记录可信性或合规用途的客户。日志覆盖范围、保存期限、不可篡改保证及合规认证均未在本版资料中说明；不能从审计能力存在推导任何认证已取得，也不能承诺某种保存或取证要求。Basic、Team 不支持审计日志，但客户提出的合规细节仍需独立保留，不能因选用 Business 就忽略未建模约束。若具体地区法规或认证是硬要求，应表达当前依据不足，而不是将一般审计说明提升成法律或合规结论。

#### 导出能力不等于审计覆盖
本节适用于同时关注数据导出与审计日志的客户。三档都支持数据导出，只有 Business 支持审计日志；两项用途与支持记录分别存在。数据能够导出不能证明导出的内容包含审计记录，审计日志受支持也不能证明可以按某种格式导出全部日志。本版未说明两项之间的具体产品连接方式，因此应分别保留客户要求的资料范围、格式和审计目标。比较套餐时可以解释已知能力差异，但不能将一项已支持能力作为另一项细节已经满足的替代证据。

#### 导出细节需要独立依据
本节适用于 Basic、Team、Business 中提出具体导出要求的客户。三档的数据导出能力明确存在，但文件格式、字段范围、容量、频率、历史跨度和处理时长未由本版资料规定。资料未说明这些内容不等于已经支持，也不等于产品明确不支持。客户若把某个导出细节作为硬要求，应保留该要求和当前未知，不能擅自删除后宣布套餐完全满足。关于审计日志留存和日志导出的细节同样不能推断，本节不会新增技术参数、服务时效或容量上限。

### 6 产品边界与常见问题

#### 私有化部署要求如何处理
本节适用于要求将澄星协作部署在自身控制环境中的客户。私有化部署在 Basic、Team、Business 三档均明确不支持，提升到最高档不会改变该事实。若这是硬需求，不能推荐任一档并宣称完全满足；也不能自行引入附加包、定制开发或特殊部署承诺解决缺口。指定地区合规、数据驻留等要求不是私有化部署的同义词，本版没有建模这些内容，应分别保留未知。解释全档不支持时应准确指向部署能力，避免把相邻但不同的约束一并说成不支持。

#### 目录外功能为何保留未知
本节适用于提出八项受控能力以外要求的客户。SCIM 自动开通、指定地区合规等内容未在本版目录中建模，没有据此增加默认不支持项，也不能套用 SSO 或审计日志的支持记录。三档的已知能力可以继续介绍，但任何未建模硬要求都不能被省略。正文没有回答某项问题时，应表明资料未说明并保留客户原意；不能把未命中资料当作否定事实。只有有效的新依据才能澄清具体要求，增加类似词语或找到相关段落本身不会扩大产品能力。

#### 套餐选择与参数有哪些界限
本节适用于在 Basic、Team、Business 之间比较能力或准备订阅参数的客户。公司人数不直接决定套餐，也不自动等于付费席位；当前没有按人数强制购买某档的规则。订阅价格、币种和计费单位由既定 Catalog 统一提供，本文不维护价表，不加入税、折扣、实施费或客户专价。演示输入的席位与期限范围也不是产品承载能力说明。套餐比较应依据明确功能与适用条件，预算硬上限等未建模约束需要保留，不能自行开展预算优化或改动目录金额。

#### 资料能够证明到哪一层
本节适用于阅读任一套餐说明、判断依据是否充分的客户。固定正文可以解释产品事实、限制和来源位置，不能证明已经完成客户集成、身份系统配置或外部服务执行。技术参数、导出格式、留存期限、地区认证和额外服务承诺若未说明，应保持未知，不凭能力名称补写。相关说明能够帮助理解能力与限制，但不会自动回答未说明的具体细节，也不能替代客户针对适用前提的明确自述。当前产品事实沿用同一 Catalog，任何说明都不能覆盖它的稳定身份、支持矩阵及唯一条件关联。

## 三 业务规则与代码中的设计依据

下面是从当前正式业务路径归纳的规则对照。知识正文、结构化产品事实和程序规则分别标明；界面提示、测试哨兵和未接入当前业务的旧模块不作为产品知识收录。本节解释规则的用途，不将校验机制等同于全面语义正确性保证。

### 1 需求与咨询分开

询问支持情况、含义、单价或实施细节，与新增购买硬需求、修改参数是不同业务行为；咨询范围单独记录。

实现出处：`app/schemas/business.py:23`；`app/services/consultation_scope.py:789`。

### 2 保留用户原意

需求保存整理后的含义和用户连续原话；目录内能力、未建模要求和歧义要求分别记录。

实现出处：`app/schemas/business.py:60`；`app/schemas/matching.py:11`。

### 3 候选与接受分开

模型先提出候选；当前流程另作一次独立核对，再由程序检查出处、任务与操作组后接受。独立核对使用同一模型配置，不是另一个模型厂商。

实现出处：`app/agents/orchestrator.py:489`；`app/services/work_state.py:718`。

### 4 数字必须明确

公司人数、计划和约数不能自动成为实际付费席位或确定期限；没有明确月份时不能默认一年。

实现出处：`app/schemas/business.py:77`；`app/services/work_state.py:632`。

### 5 输入范围是演示约束

当前计价接受1至500个整数付费席位、1至12个整数月份；这不是产品容量、购买政策或服务承诺。

实现出处：`app/schemas/pricing.py:11`；`app/schemas/pricing.py:12`。

### 6 完整需求参与匹配

程序逐档检查当前全部硬需求；未建模或歧义要求保留未知，不能删去后宣布完全满足。

实现出处：`app/services/matching.py:165`；`app/services/matching.py:187`。

### 7 最低满足档与主动选档

存在完整满足档时按目录顺序选择最低档；用户明确选择更高且满足的档位时保留其选择。指定不满足档会阻断，不通过删除需求来迁就。

实现出处：`app/services/matching.py:131`；`app/services/matching.py:136`。

### 8 无需求时只比较

尚无硬需求时可以比较套餐，但匹配结果标为comparison_only，不把它当作已完成选型。

实现出处：`app/services/matching.py:132`。

### 9 SSO同时需要规则与客户情况

Business的SSO适用判断依赖有效条件资料和用户对兼容身份提供方的明确当前自述；用户自述不等于助手验证了外部身份系统。

实现出处：`app/services/retrieval.py:168`；`app/services/matching.py:217`。

### 10 单价与总价分开

查询单价无需先补席位和月份；总价计算必须有合法套餐、实际付费席位和月份。独立计价结果不自动代表套餐适配通过。

实现出处：`app/services/pricing.py:23`；`app/services/pricing.py:42`。

### 11 金额由目录与整数运算产生

金额以人民币分存储和计算；订阅基价等于目录单价乘付费席位乘月份。模型或客户端不能任意提交单价、总价替代正式计算。

实现出处：`app/services/pricing.py:51`；`app/schemas/pricing.py:67`。

### 12 任务之间保留归属

选型与独立计价具有各自上下文；返回原任务、继续修改或开始新任务需要按实际任务处理，不能串用另一个任务的参数。

实现出处：`app/services/work_state.py:94`；`app/services/work_state.py:718`。

### 13 检索结果与引用分开

相似度用于找到相关小节；引用必须属于本次实际返回来源。分数、文件存在或来源编号有效，均不自动证明某句回答成立。

实现出处：`app/services/retrieval_worker.py:16`；`app/services/retrieval.py:119`。

### 14 引用保留原文

资料解释使用本轮实际检索，引用句必须是返回原文的连续子串，并关联真实咨询对象。不能改写后冒称原文。

实现出处：`app/tools/business.py:211`；`app/tools/business.py:569`。

### 15 来源要求归回原问题

仅要求“依据资料说明”等纯来源要求时，将其归到唯一明确的原咨询；真正新增的限流、费用或配置问题仍独立处理。

实现出处：`app/services/consultation_scope.py:748`；`app/services/consultation_scope.py:760`。

### 16 草案来自当前事实

待确认草案组合当前需求、匹配、计价及适用依据；准备和确认时检查版本、实际参数及结果一致性。

实现出处：`app/services/proposals.py:25`；`app/services/proposals.py:133`。

### 17 点击确认后保存

聊天中请求准备草案不会直接产生已保存记录；当前页面确认动作提交后，服务端复核具体草案和动作身份，再执行保存。

实现出处：`app/agents/orchestrator.py:128`；`app/main.py:284`。

### 18 旧确认许可不能沿用

继续聊天、重新进入历史或页面失效等事件会撤销旧草案确认许可；已保存记录与旧页面确认许可分别处理。

实现出处：`app/agents/orchestrator.py:92`；`app/main.py:390`。

### 19 保存结果取自实际存储

保存后以提交后的数据库记录返回编号和时间；同一动作先查原结果，无法确认时显示结果待核对，不据此自动新建动作。

实现出处：`app/agents/orchestrator.py:226`；`app/services/quotes.py:196`。

### 20 历史保留保存时事实

已保存草案保存当时的需求、套餐、价格和依据快照，后续修改形成新对象；查询历史不以当前资料重新替换旧快照。

实现出处：`app/services/quotes.py:223`；`app/schemas/quote.py:22`。

### 21 聊天记录与当前状态分开

聊天文字和已保存草案在SQLite中；当前需求、评估及未保存草案由进程内状态管理，服务重启后不会从历史文字自动恢复这些权限和事实。

实现出处：`app/services/work_state.py:1304`；`app/main.py:401`。
